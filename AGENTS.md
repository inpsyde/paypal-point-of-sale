# AGENTS.md

PayPal POS for WooCommerce (formerly Zettle POS Integration): syncs the WooCommerce product catalog to the PayPal POS product library and keeps stock in sync both ways, through the PayPal POS (Zettle) API and its webhooks.

## Critical rules

- PHP 8.2 compatible. CI runs PHP 8.2, 8.3, and 8.4, so no 8.3+ syntax or functions (typed class constants, `#[\Override]`, `json_validate()`).
- Edit modules through `modules.local/`, never through `modules/`: `modules/` holds Composer's symlinks to them, and the rules and hooks only match `modules.local/` paths. `vendor/` and each module's `assets/` are generated; `modules.php` is regenerated by Composer.
- Never run the root integration tests unasked: they call the live PayPal POS account in `.env.phpunit`, and some delete every product in it. See Commands.
- A change to an external surface (hook, stored data, runtime assumption) needs a backward-compatibility statement in the PR. See below.

## Backward compatibility

The contracts with third-party code are hooks, stored data, and assumptions about the runtime. PHP classes, interfaces, and methods are not contracts, even when the container exposes them: change or remove them freely.

Assume that unseen code uses every external surface. If you cannot establish the impact of a change, stop and ask.

- **Hooks:** never remove a hook, or remove or reorder its arguments. Add new arguments at the end. A change to when or whether a hook fires can also break consumers. Rename a hook only through `src/DeprecatedHooks.php`, which keeps firing the old name through `apply_filters_deprecated()` / `do_action_deprecated()`.
- **Hook data:** keep callback parameters untyped (silence `Syde.Functions.ArgumentTypeDeclaration.NoArgumentType` for them), and validate the value before it reaches typed code. Validate the final return value of every filter this plugin fires.
- **Global state:** code runs in admin, REST, WP-CLI, cron, queue, webhook, and front-end contexts. The session and the cart exist only on front-end requests, and `$post` / `$wp_query` only where WordPress sets them up. Guard each dependency: `function_exists`/`class_exists`, `isset`, `did_action`, and a check that `WC()` and its component exist before `WC()->…`. Webhook, queue, and cron paths are the most exposed. Do not use container services before the module has booted.
- **Multisite:** site and network data live in different places (`get_option` vs `get_site_option`, per-site tables, roles, upload paths). A PR that reads or writes site state (credentials, onboarding, sync settings, ID maps) states whether it works on multisite, and says so when it was not tested there.
- **Install layout:** WordPress can run in a subdirectory, with a moved `wp-content`, or behind a proxy. Derive paths and URLs (`plugins_url()`, `plugin_dir_path()`, `wp_upload_dir()`; `home_url()` is not `site_url()`), never concatenate them. This is most important for the webhook URL registered with PayPal POS.

### Migrations

`paypal-point-of-sale.migrate` fires on `plugins_loaded` whenever the stored plugin version differs from the current one (`zettle-pos-integration.php`). Modules hook their migrations onto it.

- The action fires on every version change, upgrades and downgrades alike. A migration must be idempotent: check whether its work is already done before it acts.
- The previous release must still work on migrated data. If old code cannot read the new format, the change needs a deprecation window.

## Project structure

The plugin uses Syde Modularity: each feature is a module in `modules.local/`, wired through `services.php` and `extensions.php` into a PSR-11 container. Composer installs each module as a path repository into `modules/`.

```
zettle-pos-integration.php  # Plugin entry point, version check, migrate/activate hooks
bootstrap.php               # Container init, module loading
modules.php                 # Generated module list (Composer dump-modules)
uninstall.php               # Cleanup on uninstall
src/                        # Core: PluginModule, DeprecatedHooks
modules.local/              # Module sources: src/, services.php, extensions.php, own composer.json
packages.local/             # Local Composer packages
stubs/                      # PHPStan stubs
tests/PHPUnit/              # Root PHP tests: Unit/, Integration/ (live API), Helper/, Stubs/
```

- Add behavior through module services and extensions, not globals. `ExecutableModule::run()` only registers hook callbacks.
- `paypal-pos-php-sdk` is the PayPal POS API client; `paypal-pos-sync` and `paypal-pos-queue` run the product and stock sync as queued jobs; `paypal-pos-webhooks` receives the PayPal POS webhooks.
- The admin JS (product settings, debug, shared assets) is built per module from `modules.local/*/resources/`.

## Conventions

- Text domain: `paypal-point-of-sale`. New hooks use the `paypal-point-of-sale.` prefix; existing `inpsyde.zettle.*` and `paypal-pos.*` hooks keep their names.
- User-facing name: "PayPal Point of Sale" in the plugin UI, "PayPal POS" in `readme.txt`. "Zettle" stays in code, the API, and legacy hook names only.
- American English in code, comments, docs, and commits ("canceled", "behavior").
- `dev/main` is the source branch and the PR base. Feature branches are `dev/POS-<number>-<slug>`. Every branch without the `dev/` prefix (`main`, `release/*`, `POS-*`) is a generated build artifact; never diff or branch from it.
- 4 spaces for PHP, JS, and JSON. Match the surrounding file for YAML.
- PHPCS (`Syde-Extra`), PHPStan level 8.
- PR descriptions follow the `/describe-pr` guideline. The `readme.txt` changelog is written at release time, not per PR.

## Commands

Run every command through DDEV: `ddev composer`, `ddev npm`, and `ddev exec` for anything else. The `Makefile` wraps the common ones.

| Task                   | Command                                                                     |
|------------------------|-----------------------------------------------------------------------------|
| Start the site         | `make setup` (`ddev start && ddev orchestrate`); `make reset` reinstalls    |
| Build JS/SCSS          | `make build`, or `make watch`                                               |
| Reinstall dependencies | `make install`                                                              |
| PHPCS + PHPStan        | `make lint`; auto-fix with `make fix-lint`                                  |
| Root PHP unit tests    | `ddev exec vendor/bin/phpunit tests/PHPUnit/Unit [--filter <keyword>]`      |
| Module dependencies    | `ddev composer install --working-dir=modules.local/<module>`                |
| Module PHP tests       | `ddev exec --dir /var/www/html/modules.local/<module> vendor/bin/phpunit`   |

Always pass `--dir` for a module: `ddev exec bash -c 'cd … && …'` drops the `cd` and runs the root suite instead. Root PHP tests need `.env.phpunit` (copy `.env.phpunit.dist`).

All unit tests, root and every module, without the live API:

```bash
ddev exec 'vendor/bin/phpunit tests/PHPUnit/Unit && for c in modules.local/*/phpunit.xml.dist; do (cd "$(dirname "$c")" && { [ -d vendor ] || composer install -q --no-progress; } && vendor/bin/phpunit) || exit 1; done'
```

The root `phpunit.xml.dist` also runs `tests/PHPUnit/Integration/`, which calls the live PayPal POS API with the credentials in `.env.phpunit`. `make test` and `./phpunit.sh` include it, and `--no-sync` only skips the `sync` group, whose tests (`InitialSyncTest`, `InventoryTrackingTest`) delete every product in the account. Run them only against a test account.

Site: https://paypal-point-of-sale.ddev.site (URLs in `ddev describe`). Webhooks need a public tunnel: `make ngrok`, see `README.md`.
